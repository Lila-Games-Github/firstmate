==================== ACT 3: the deadlock that was left behind - two records, one slot ====================
# This is the state the incident actually reached: the spawn took the slot,
# so the scout's record names it too and now holds its claim, while the
# pipeline's record still names the same copy. The scout has finished and
# its report is in the firstmate home; the pipeline task landed long ago.
# (the spawn that took the slot re-prepared it onto a detached base, which
# is what replaced the pipeline branch checkout in the incident)

--- 1. the ordinary command, on the long-landed pipeline record

$ bin/fm-teardown.sh frogpile-ui-pipeline
REFUSED: task frogpile-ui-pipeline's recorded worktree /tmp/fm-demo-target/pool/1/repo is also task frogpile-jev-usecases-research's recorded worktree.
Returning that pool slot would kill frogpile-jev-usecases-research's processes and reset its copy, so nothing was changed - not even with --force.
Reconcile whichever record is wrong (bin/fm-crew-state.sh frogpile-ui-pipeline; bin/fm-crew-state.sh frogpile-jev-usecases-research), then re-run teardown.
When both records are genuinely stuck on one slot, bin/fm-teardown.sh --reconcile-slot retires the record whose own work is provably safe without touching the slot.

==================== ACT 4: bin/fm-control.sh <id> relaunch, into a copy another record owns ====================
# The other way into the same deadlock: the captain relaunches the agent of
# a task whose record still names a slot a different live record now owns.
